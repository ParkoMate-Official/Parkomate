System Architecture & Workflow Specification

Multi-User Factory Floor Task Flow

An industrial-grade, decoupled task coordination system allowing factory administrators to assign operators any combination of the four production phases—Programming, Testing, Labeling, and Packaging. Powered by an asynchronous SQLite-backed Work Queue, instant board handoffs, state rehydration, and zero bottlenecking across single or networked stations.

Production Problem & Solution Model

Fully Implemented

In previous generation bench setups, a single technician was required to flash the board, measure ambient temperature and voltages, scan QR labels, and box the finished device consecutively on one PC. If a hardware flasher lagged or a thermal probe required stabilization, the entire production pipeline stalled.

❌ Legacy Bottlenecks

  • Single operator tied to all 4 stages consecutively.
  • No task specialization (one person doing hardware flashing, electrical testing, and packaging).
  • Idle factory PCs unable to pick up already-flashed boards.
  • If Station 1 rebooted or logged out, board state was abandoned.

✅ Parkomate 2.0 Multi-User Flow

  • Flexible Task Granularity: Admin can assign 1, 2, 3, or all 4 tasks per operator.
  • Asynchronous Work Queue: Automatic handoff to SQLite work_queue when next stage is unassigned.
  • AppBar Queue Popup: Downstream operators see waiting boards with one-click "Pick Up".
  • Deep State Rehydration: All previous check outcomes, telemetry readings, and MAC/QR data seamlessly restore.

Step-by-Step Execution Lifecycle

1

Stage Execution & Check Validation

The operator conducts their assigned stage (e.g. flashing firmware in Programming). Checks A1 through A4 complete with PASS criteria. The primary action button changes to "Submit and Next Stage" [Enter].

2

Permission Gate & Automatic Handoff

When StationController.advance() is triggered, the engine calculates the next sequential stage (Stage.TESTING). It inspects operator.effective_stages: 

if operator is not None and new not in operator.effective_stages:
    self.ctx.repos.work_queue.enqueue(
        device_row_id=state.device_row_id,
        mac_address=state.mac_address,
        device_id=state.device_id,
        stage=new.value,
        source_session_id=self.session.id,
    )
    self.toast.emit(t("queue.handoff"))
    self._next_device()
    return
3

Hardware Release & Bench Reset

Station 1 immediately executes _release_board(), closing serial COM handles and camera framegrabbers. The bench resets cleanly to the operator's first assigned stage, ready for the next incoming board with zero downtime.

4

Downstream Inbox Discovery & Queue Pickup

Operator 2 (assigned to Testing) sees the inbox icon update in the top AppBar. Clicking it opens the WorkQueuePopup listing waiting boards. Clicking Pick Up invokes: 

item = self.ctx.repos.work_queue.pick(queue_id, self.operator.id, self.session.id)
self.ctx.workflow.resume_device(item.device_row_id, item.current_stage)
5

Full State Rehydration

WorkflowEngine.resume_device queries the database for all historical checks, marks, voltage readings, and device IDs previously recorded. The Station UI instantly displays the device in Stage B with previous stages marked done in the Stepper.

Network & Multi-PC Deployment Topology

Industrial LAN Setup

Parkomate Station supports two deployment modes: Multi-PC Networked Assembly Line (ideal for higher volume production) and Single-PC Multi-Shift Station.

Mode 1: Networked Multi-PC Line

Each physical PC on the factory line runs Parkomate Station connected to a shared SQLite database with Write-Ahead Logging (WAL) over SMB/NFS or local cluster storage:

  • PC 1 (Flashing Station): ESP32 programmer fixture. Operator 1 logs in (Assigned: A).
  • PC 2 (Testing Station): Oscilloscope & DMM bench. Operator 2 logs in (Assigned: B).
  • PC 3 (Packing Station): Barcode scanner & label printer. Operator 3 logs in (Assigned: C, D).
  • Coordination: SQLite atomic transactions ensure exact-once pickup with zero race conditions.

Mode 2: Single-PC Batch Processing

Used when a single physical bench is utilized by different technicians during different shifts or batch runs:

  • Shift 1: Operator flashes a batch of 50 boards. All 50 boards enqueue into work_queue.
  • Shift 2: QA technician logs in. All 50 boards appear in the AppBar Queue.
  • Pickup: QA technician tests each board sequentially without needing to reflash or plug ESP32 programmer.
  • Total History Preserved: Flasher's operator code and tester's operator code both recorded on final certificate.

Database Schema: work_queue Table

Migration 0004

Defined in src/parkomate/data/migrations/0004_task_assignments.sql. Designed with strict referential integrity, indexes for high-speed queue polling, and stage check constraints: 

CREATE TABLE work_queue (
    id                INTEGER PRIMARY KEY,
    device_row_id     INTEGER NOT NULL REFERENCES devices(id),
    mac_address       TEXT    NOT NULL,
    device_id         TEXT,
    current_stage     TEXT    NOT NULL CHECK (current_stage IN ('programming', 'testing', 'labeling', 'packaging')),
    ready_at          TEXT    NOT NULL,
    picked_by         INTEGER REFERENCES operators(id),
    picked_at         TEXT,
    completed_at      TEXT,
    source_session_id INTEGER REFERENCES sessions(id),
    target_session_id INTEGER REFERENCES sessions(id),
    status            TEXT    NOT NULL DEFAULT 'waiting'
                      CHECK (status IN ('waiting', 'in_progress', 'done', 'cancelled'))
);

CREATE INDEX ix_work_queue_stage  ON work_queue (current_stage, status);
CREATE INDEX ix_work_queue_device ON work_queue (device_row_id);
CREATE INDEX ix_work_queue_picked ON work_queue (picked_by) WHERE status = 'in_progress';

Work Queue State Machine

Status Code Meaning Triggering Event Next Available Actions
waiting Board enqueued and ready for pickup StationController.advance() when next stage is unassigned Visible in AppBar Queue popup to authorized operators; "Pick Up" button enabled.
in_progress Claimed and actively under test on bench WorkQueueRepo.pick(queue_id, op_id, session_id) Can transition to done on stage completion or cancelled if rejected.
done Stage successfully finished by picking operator WorkQueueRepo.complete(queue_id) Terminal state for this queue item; board advances to next stage or finishes packaging.
cancelled Device was rejected or abandoned during testing WorkQueueRepo.cancel(queue_id) Device placed in red Reject Box (A, B, C, or D). Terminal state.

Fail-Safe Mechanics & Edge Case Protection

Zero Production Loss

1. Rejection Takeover Isolation

If a board fails electrical testing at Stage B, the Reject Takeover Overlay engages immediately with the exact physical reject box letter (Box B). The item in work_queue is cancelled, ensuring broken hardware can never be picked up by packaging operators.

2. Station Crash & Session Rehydration

If power to PC 2 fails while testing, RecoveryManager on reboot detects the unfinished session. The board remains safely recorded in devices and can either be resumed or marked for re-testing via the Repair Tab.

3. Concurrent Pickup Protection

If two operators on separate stations attempt to click "Pick Up" on the same waiting board simultaneously, SQLite transaction isolation ensures only the first query updates status = 'in_progress'. The second operator receives an immediate notification that the board has already been claimed.

4. Active Bench Locking

An operator is prevented from picking up a board from the queue while they already have another device active on the bench (RecordStateError("a device is already on the bench")), guaranteeing one physical board per operator at all times.
